Self-hosting

One binary, one data directory, one service. This page is the operational contract: what to install, what to back up, and what to check when Docker or TLS misbehaves.

Requirements

  • Linux x86_64 or aarch64 for the server. The CLI also runs on macOS; a macOS server is fine for a local instance.
  • Docker for container builds and container apps. Static sites need only the binary. The service user needs access to the Docker socket.
  • A domain and the ability to create A/CNAME records. Edge mode needs inbound TCP 80 and 443.
  • Disk: at least 1 GB free before an upload is accepted; 5–10 GB is a comfortable baseline for builds and backups. SQLite is bundled, there is no external database.
  • systemd (or another supervisor) so the process survives logout and reboot. A dedicated non-root user is strongly recommended.

Install the binary

bash
curl -fsSL https://dok.djt-group.com/install.sh | sh
export PATH="$HOME/.local/bin:$PATH"
dok --version

The installer downloads dok-<os>-<arch> from the latest GitHub release into ~/.local/bin. If no release asset exists, it builds from source with Cargo. To build yourself:

bash
git clone https://github.com/OckoTajny/dok.git
cd dok
cargo build --release
install -m755 target/release/dok ~/.local/bin/dok

Put the binary somewhere stable. The unit below assumes ~/.local/bin/dok; change ExecStart if you installed it to /usr/local/bin.

Edge mode

Edge mode makes dok the public TLS terminator: it binds :80 and :443, redirects HTTP to HTTPS, answers ACME HTTP-01 and TLS-ALPN-01 challenges, and issues certificates for every project host and custom domain into <data>/acme.

bash
dok serve --edge \
  --base-domain apps.example.com \
  --public-host dok.example.com \
  --dashboard-origin https://dok.example.com \
  --acme-email you@example.com

DNS must already point dok.example.com and *.apps.example.com at this machine. The host set is recomputed every 15 seconds, so adding a project or domain does not require a restart. Do not run edge mode on a host where Traefik or Caddy already owns ports 80/443.

Privileged ports

Ports below 1024 need privilege. Run edge mode as root only if you accept that; otherwise grant the binary CAP_NET_BIND_SERVICE (sudo setcap 'cap_net_bind_service=+ep' ~/.local/bin/dok, and reapply after an upgrade) or, for a system unit, add AmbientCapabilities=CAP_NET_BIND_SERVICE. The least surprising option is to keep Traefik/Caddy on 80/443 and run dok on a high port.

Run it as a service

Create a user unit at ~/.config/systemd/user/dok.service. Adjust the hostnames, ports and Traefik directory for your setup; this example is the plain-HTTP-behind-Traefik layout.

ini
[Unit]
Description=dok deploy platform
After=network-online.target docker.service
Wants=network-online.target

[Service]
ExecStart=%h/.local/bin/dok serve \
  --http-port 8080 \
  --public-host dok.example.com \
  --dashboard-origin https://dok.example.com \
  --base-domain apps.example.com \
  --traefik-dir /etc/traefik/dynamic \
  --data %h/.local/share/dok
EnvironmentFile=-%h/.config/dok/env
Environment=RUST_LOG=dok=info
Restart=always
RestartSec=3

[Install]
WantedBy=default.target
bash
mkdir -p ~/.config/systemd/user
# write the unit, then:
systemctl --user daemon-reload
systemctl --user enable --now dok
systemctl --user status dok --no-pager
loginctl enable-linger "$USER"   # keep the user service after logout

Secrets and optional settings belong in ~/.config/dok/env, mode 0600. The unit reads it with EnvironmentFile=-, so a missing file is not fatal:

bash
printf 'DOK_HOOK_SECRET=%s\n' "$(openssl rand -hex 16)" > ~/.config/dok/env
chmod 600 ~/.config/dok/env
systemctl --user restart dok

Use journalctl --user -u dok -f for startup logs. If the service cannot reach Docker, see Docker access.

Behind Traefik

If you already run Traefik, keep it and let dok speak plain HTTP on a private port. Set --trusted-proxy to the proxy's CIDR so X-Forwarded-Proto and client IPs are honoured; only loopback is trusted by default.

bash
dok serve \
  --http-port 8080 \
  --base-domain apps.example.com \
  --public-host dok.example.com \
  --dashboard-origin https://dok.example.com \
  --traefik-dir /etc/traefik/dynamic \
  --trusted-proxy 100.64.0.0/10

A minimal file-provider configuration for the dashboard route:

yaml
http:
  routers:
    dok-https:
      entryPoints: [https]
      rule: Host(`dok.example.com`)
      service: dok
      tls:
        certResolver: letsencrypt
    dok-http:
      entryPoints: [http]
      rule: Host(`dok.example.com`)
      middlewares: [dok-redirect-https]
      service: dok

  middlewares:
    dok-redirect-https:
      redirectScheme:
        scheme: https
        permanent: true

  services:
    dok:
      loadBalancer:
        servers:
          - url: http://127.0.0.1:8080
  • certResolver must match the resolver name in your Traefik static configuration. dok writes certResolver: letsencrypt into its per-app routers, so either name your resolver letsencrypt or adjust the generated file.
  • dok writes one Host() router per app, domain and preview into --traefik-dir. Traefik only requests a certificate when it sees the exact host.
  • With many preview deployments, use a wildcard certificate from Traefik's DNS-01 resolver. dok itself does not implement DNS-01 and cannot issue wildcard certificates.
  • The directory must be writable by the dok service user. Traefik hot-reloads file-provider changes; do not restart it for every deploy.

The data directory

Everything dok owns is under --data, default ~/.local/share/dok. The process sets umask 077, so new files are private by construction.

dok.db          SQLite database, mode 0600
dok.db-wal      write-ahead log, mode 0600
dok.db-shm      shared-memory file, mode 0600
builds/         retained build trees, ten per environment
repos/          bare git repositories created by dok git-init
acme/           certificates issued by edge mode
logs/           deploy logs
locks/          per-project deploy locks
backups/        consistent database snapshots
traefik/        generated per-app routers, if enabled
initial-token   first-run token, before dashboard setup
tmp/            upload staging; swept at startup

The directory is 0700. The database, its WAL/SHM files and every backup are 0600, so other local accounts cannot read environment secrets.

Backups and restore

dok writes a consistent SQLite snapshot at startup and every 24 hours. The default keeps seven; change it with --backup-keep N or disable it with 0.

  • Backups cover the database: users, teams, projects, deploys, env vars, domains and sessions.
  • If you use git-push projects, copy repos/ alongside the database.
  • If you use edge mode, copy acme/ so certificates survive a restore.
  • Copy builds/ only if you need the retained artifacts; it is large and can be rebuilt.

To restore, stop the service, replace the database, remove stale WAL/SHM files, then start it again. Migrations run automatically on start.

bash
systemctl --user stop dok
cp ~/.local/share/dok/backups/dok-2026-11-10.db ~/.local/share/dok/dok.db
rm -f ~/.local/share/dok/dok.db-wal ~/.local/share/dok/dok.db-shm
systemctl --user start dok
systemctl --user status dok --no-pager
Test the restore

A backup you have never restored is a hope. Copy the data directory to a test host, restore there, and verify that the dashboard opens and a project serves before you need it in an incident.

Upgrades

bash
systemctl --user stop dok
# take a fresh backup or copy backups/ now
curl -fsSL https://dok.djt-group.com/install.sh | sh
systemctl --user start dok
dok --version

Re-running the installer is idempotent: it replaces ~/.local/bin/dok. The SQLite schema is migrated in place on start. If you build from source, replace the binary and restart the service the same way. Keep a backup from <data>/backups before a major upgrade.

Docker access

Container deploys fail with “permission denied” when the service user cannot read the Docker socket. Add the user to the docker group (log out and back in for the group to apply), or use an ACL:

bash
sudo usermod -aG docker "$USER"
# or, without a group change:
sudo setfacl -m u:"$USER":rw /var/run/docker.sock
systemctl --user restart dok
docker version

The repository ships deploy/docker-socket-acl.conf, a systemd drop-in that reapplies the ACL when the Docker socket is recreated. Without it, a Docker restart can silently remove access.

Keep-awake (optional)

If dok runs on a laptop or desktop that suspends, the sites go down with it. The repository includes a small unit that inhibits sleep:

bash
sudo install -m644 deploy/dok-keepawake.service /etc/systemd/system/
sudo systemctl enable --now dok-keepawake.service

This is not needed on a normal always-on server, and it is the wrong tool for a machine you want to sleep on a schedule.

Security checklist

  • Run dok as a dedicated non-root user; do not expose the Docker socket over TCP.
  • Firewall everything except 80/443 (edge) or the private proxy port.
  • Set --trusted-proxy only to the proxy network you actually control.
  • Keep ~/.config/dok/config.toml and any token file at mode 0600.
  • Back up backups/, repos/ and acme/ off the machine.
  • Keep the binary and the host OS patched; re-run the installer for dok upgrades.
