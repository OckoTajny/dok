Teams & tokens

Projects belong to teams; tokens belong to people. This page covers the role matrix, invite links, token lifecycle and the rules that keep secrets out of the wrong scope.

How teams work

Every project belongs to exactly one team. The first user created during dashboard setup owns the first team; additional teams can be created from the dashboard or the CLI. A personal API token acts as its user, so it sees exactly the projects that user can see through team membership.

Roles are enforced on the server, not hidden in the UI. A viewer's token cannot deploy, and a member's token cannot change environment variables or domains.

Create a team

bash
dok team create "Acme Studio"
dok teams
dok projects create billing --team acme-studio

Team names are labels; commands accept either the team slug or its id. dok teams shows both your role and the identifier to use. Existing projects are not moved between teams by a rename or a new team; create the project in the right team from the start.

Invite people

Invite links are single-use and expire after seven days. The default role is member.

bash
dok team invite acme-studio --role member
dok team invites acme-studio

The command prints a link like https://dok.example.com/join/<token>. Send it over a channel you trust. Opening it shows the team name and who invited you before the passkey prompt; an invalid or expired invite is reported immediately rather than after authentication.

  • Only owners can grant admin or owner.
  • Admins can invite member and viewer.
  • Revoke a link you no longer need: dok team revoke <team> <token>.
  • An invite is consumed when the person joins; it cannot be replayed.

Roles and what they can do

ActionViewerMemberAdminOwner

Remove members, change rolesNoNoLimitedYes

Secret env values stay masked for everyone after they are written, including owners. Membership changes are checked server-side: the last owner cannot be demoted, and an admin cannot promote themselves or anyone else to owner.

bash
dok team members acme-studio
dok team role acme-studio sam admin
dok team remove acme-studio sam

The join flow

  1. The invitee opens the link and sees the team and inviter.
  2. They register a passkey (or sign in with an existing one on that dashboard host).
  3. dok creates the membership with the role recorded on the invite and consumes the link.
  4. The new member sees the team's projects on their next dashboard visit or API call.

Passkeys are bound to the dashboard hostname. An invite link must use the same host as --dashboard-origin, or WebAuthn will reject the ceremony.

Personal API tokens

Tokens are personal, not team-wide. Create one in Account → API tokens, or with the CLI once you are logged in:

bash
dok tokens create --name ci
dok tokens list
dok tokens revoke 4f2c9a1b8e70

The secret is printed once and stored by the server as a SHA-256 hash; tokens list returns only ids and names. Every request uses a bearer header:

bash
curl -fsS https://dok.example.com/api/v1/whoami \
  -H "Authorization: Bearer $DOK_TOKEN"
  • The token inherits the user's current role in each team. Demoting a user takes effect on their next request; no token reissue is needed.
  • Rate limits are per user: 600 API requests per minute and 20 deploys per minute.
  • Tokens minted before first-run setup is complete stay inactive until the dashboard setup claims them. If in doubt, issue a fresh token.

Token and secret safety

  • Do not put tokens in argv. They appear in shell history and ps. Use DOK_TOKEN, --token-file, or the saved ~/.config/dok/config.toml (mode 0600).
  • Give CI its own token. Name it after the pipeline, store it in the CI secret store, and revoke it when the job is retired.
  • Rotate on offboarding. Removing a person from a team cuts access to that team, but their personal token remains valid for other teams. Tokens can only be revoked by the account that owns them, so ask the owner or revoke from their session.
  • Secrets stay write-only. Use dok env --secret for API keys. Non-secret production values are inherited by preview and development; secrets are not, because preview URLs are public.
  • Passkeys, not passwords. The dashboard has no password login. Per-project basic auth is separate, stored as an argon2 hash, and intended for staging or simple gates — not as a replacement for application auth.
  • Trust the dashboard host only. The dashboard, passkey endpoints and token API answer only on the configured dashboard host and localhost. Application hosts never expose a project list.
Least privilege in practice

Use viewer for stakeholders who need logs and status, member for developers who ship, admin for whoever owns domains and secrets, and keep owner for the smallest possible group.

Removing people

bash
dok team remove acme-studio sam
dok team members acme-studio

Removal takes effect immediately for team-scoped resources. The user keeps their account and any other team memberships. If the person is leaving entirely, also revoke their personal tokens from their account and remove their passkey from the dashboard's account settings.
