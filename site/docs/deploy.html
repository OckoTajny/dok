Deploying apps

A push is packed, uploaded, extracted, detected, built and switched. This page explains each decision point, including the limits that stop a bad archive before it runs.

How a push works

A deploy is deliberately boring:

  1. Pack. The CLI walks the directory, skips files that should never leave your machine, and writes a gzipped tar.
  2. Upload. The archive is streamed to POST /api/v1/projects/<app>/deploy. The server enforces the size and entry limits while it writes.
  3. Extract. The archive is unpacked into a fresh build directory under builds/. Path traversal and symlinks are rejected.
  4. Detect. A Dockerfile wins. Otherwise dok looks for a static site, Node, Python or Go project. Unknown projects fail here with an explanation.
  5. Build and start. Containers are built and started on a temporary loopback port. dok waits for a real HTTP response before touching production.
  6. Switch. The proxy pointer moves to the new container or static directory. The old one is retired only after the new one answers.

Static sites switch a directory pointer; containers get a new process first, then the route. A failed build never replaces the running version.

What gets uploaded

The CLI uses the same ignore rules for every project, so you do not need a .dokignore:

  • .git, node_modules, target, .venv and __pycache__ are always skipped.
  • Dotfiles are skipped, with one exception: .well-known is kept so ACME and app verification files can be served.
  • .env and every .env.* file are skipped. Secrets belong in dok env, not in the upload.
  • Symlinks are skipped rather than followed, so a hostile repository cannot smuggle host files into a build.

Limits are enforced server-side: 200 MB compressed, 20,000 archive entries and 500 MB uncompressed. The server also refuses an upload when the data filesystem has less than 1 GB free.

Need a file that is normally ignored?

Commit it with a different name, generate it during the build, or put it in a subdirectory that is not on the skip list. There is no flag that disables the secret-file filter.

Static sites

If the uploaded tree has an index.html at its root and no manifest that says otherwise, dok serves it as static files. No Docker, no container, no port.

bash
dok push ./site --app landing
  • / serves index.html; a directory path serves its own index.html.
  • Extensionless paths fall back to the root index.html, which covers client-side routers that use clean URLs.
  • Only GET and HEAD are allowed. Dotfile paths return 404.
  • ETags and optional compression are handled by the proxy; dok proxy set can enable compression.

For a built frontend (Vite, Astro, Svelte, Nuxt), push the directory that contains the final index.html — usually dist/, build/ or .output/public/ — or let auto-detection build it for you.

Container apps

A Dockerfile at the root wins over static detection. Put it anywhere else and point to it with dockerfile in dok.toml.

The container port is chosen in this order:

  1. --port on dok push.
  2. port in dok.toml.
  3. The first EXPOSE in the Dockerfile.
  4. 3000.

Every container runs with a memory limit (default 512 MB, clamped to 32–4096 MB) and a CPU limit (default 1.0, clamped to 0.1–4.0). Environment variables are passed through a temporary 0600 env file that is deleted after the container starts.

Readiness, not just “started”

Docker can accept a connection before your app serves HTTP. dok waits for a real non-5xx response (404 is fine) before switching production, so a crash loop does not take the site down.

Auto-detection

No Dockerfile? dok builds one of these small images. An explicit framework in dok.toml overrides the guess.

Detected project types
DetectedSignalWhat runs
Node apppackage.json with a start scriptnpm start, with npm run build first if that script exists. Port 3000.
Node static buildpackage.json with build but no startnpm run build, then serve on port 3000. Output: Nuxt .output/public, CRA/SvelteKit build, otherwise dist.
Pythonrequirements.txt or pyproject.tomlpython main.py, falling back to python app.py. Port 8000.
Gogo.modStatic binary built in a Go stage, run on Alpine. Port 8080.
Staticindex.html, or framework = "static"Files served directly. No container.

Accepted framework hints include static, node, next, vite, react, remix, nuxt, svelte, astro, python, flask, django, fastapi, go and golang.

A package.json with neither start nor build is only served as static if an index.html exists at the root. Without one, the deploy fails and tells you to add a script or a Dockerfile — easier to debug than a blank page.

dok.toml

The file is optional and every field is optional. It lives at the project root and is read on every deploy.

toml
name = "my-app"
port = 3000
domain = "my-app.example.com"
# dockerfile = "Dockerfile"
memory_mb = 512
cpus = 1.0
# framework = "static"
dok.toml fields
FieldTypeMeaning
namestringProject name used when --app is omitted.
portintegerContainer port; overrides Dockerfile EXPOSE.
domainstringPrimary custom domain to attach.
dockerfilestringPath inside the uploaded tree. Absolute paths and .. are rejected.
memory_mbintegerDocker memory limit; default 512, clamped to 32–4096.
cpusfloatDocker CPU limit; default 1.0, clamped to 0.1–4.0.
frameworkstringForce a detection hint, or static to skip containers.

Environments and variables

Every project has three variable scopes: production, preview and development.

bash
dok env my-app API_URL=https://api.example.com
dok env my-app STRIPE_KEY=sk_live_... --secret
dok env my-app DEBUG=1 --env preview
dok env pull my-app
  • Non-secret production values are inherited by preview and development, then overridden by values set in that scope.
  • Secret production values are not inherited. Preview URLs are public, so a production secret only reaches preview if you set it explicitly there.
  • Secret values are write-only after saving. dok env pull prints ***, and viewers only ever see key names.
  • Values cannot contain newlines and are capped at 64 KB. Store multiline data base64-encoded or inside the image.

Preview deployments

A preview is a normal build in a separate environment. It gets its own artifact, its own container and its own hostname:

bash
dok push . --app my-app --env preview
# → https://my-app-4f2c9a1b.apps.example.com

The suffix is the first eight characters of the deploy id. Previews never move the production pointer, so you can push a branch, open the URL, and leave production alone.

The API accepts the same choice through X-Dok-Env: preview or ?env=preview. In edge mode each preview host gets its own certificate; dok does not implement DNS-01, so it cannot issue a wildcard certificate itself. With many previews, terminate TLS in an external proxy with a wildcard and run dok behind it.

Promote and rollback

List the deploys, then point production at a successful one:

bash
dok deploys my-app
dok promote my-app 4f2c9a1b
dok rollback my-app 9e8d7c6b

rollback is an alias for promote; both run a build on production. If the recorded image still exists, dok starts it directly. Otherwise it rebuilds from the retained build directory. The deploy must have status ok and its build tree must still exist.

The last ten builds per environment are kept. The current production deploy is always protected from cleanup; older build trees and the previous image tag are removed on the next successful deploy.

Git deploys

dok git-init creates a bare repository in the data directory and wires a post-receive hook to dok deploy-git.

bash
dok git-init my-app
git remote add dok /home/you/.local/share/dok/repos/my-app.git
git push dok main

Pushing any branch runs the hook with that ref; the configured production branch decides whether the result becomes production. For a remote SSH user, that user needs read/write access to the data directory, or use the local file://-style path shown above.

You can also point a project at an existing repository and let dok redeploy clone it:

bash
dok git my-app https://github.com/acme/my-app.git
dok webhook my-app --secret "$(openssl rand -hex 24)" --branch main

Repository URLs are limited to public https://, ssh:// and git@host:path remotes. Loopback, private, link-local and cloud-metadata addresses are refused, so a project cannot become an SSRF probe. For an internal git server, opt in explicitly with DOK_REPO_ALLOW_HOSTS.

GitHub webhooks

The endpoint is POST /api/v1/hooks/github/<app>. dok verifies X-Hub-Signature-256 as an HMAC over the raw body, ignores pushes outside the configured branch, and records the commit SHA, message and author on the deploy.

bash
dok webhook my-app --secret "$(openssl rand -hex 24)" --branch main
dok webhook my-app

In GitHub, add a webhook with content type application/json, the URL above, and the same secret. dok git-init also generates a per-project secret and branch. DOK_HOOK_SECRET remains a legacy fallback for projects without a per-project secret.
