Domains & TLS

Default hosts need no DNS. Custom domains are one command plus one record; certificates follow automatically once the name resolves to the machine that terminates TLS.

The default hostname

Every project gets <app>.<base-domain> unless a primary custom domain is set, where the base domain is whatever you passed to dok serve --base-domain. If you started dok with --base-domain apps.example.com, a project named hello is live at https://hello.apps.example.com.

  • The default host is created with the project; no DNS record is needed when the base domain already has a wildcard A/AAAA record pointing at the server.
  • The dashboard host and the base-domain apex are reserved and never proxied to an app.
  • A custom domain cannot be added on *.<base-domain>; that namespace belongs to dok's own routing.
  • Setting a primary custom domain replaces the default host: <app>.<base-domain> is no longer routed while a primary custom domain is active. Add extra domains instead if you want to keep both.

Add a custom domain

Three ways, same result:

bash
dok domain hello hello.example.com        # set the primary domain
dok domains list hello

Or open the project in the dashboard, choose Domains, and add the host. Or call the API directly:

bash
curl -fsS -X POST https://dok.example.com/api/v1/projects/hello/domains \
  -H "Authorization: Bearer $DOK_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"domain":"hello.example.com"}'

dok validates the hostname, refuses a domain already owned by another project, writes the route and adds the host to the certificate set. There is no separate “verify” button to wait for.

What dok checks — and what it does not

dok cannot see your DNS provider, so it does not pretend to run a DNS preflight. Adding a domain succeeds immediately; what you watch afterwards is the certificate state. If DNS is wrong, the domain exists but the certificate stays pending until the host resolves to this server. The exact records to create are below.

The DNS records

For the reference deployment, point the hostname at dok.solta.tech with a CNAME, or directly at the server IPv4 with an A record:

Reference deployment DNS records
TypeNameValueUse when
CNAMEdok.example.comdok.solta.techAny non-apex hostname. Preferred: the target can move without changing your record.
Adok.example.com130.61.16.91Apex domains, or providers that flatten or forbid CNAME.
CNAMEwww.example.comdok.example.comOptional www alias; pair it with a redirect below.

For your own installation, replace the target with your dashboard host (the machine terminating TLS) and the IPv4 with your server's address. dok.solta.tech currently resolves to 130.61.16.91; both forms reach the same edge.

Apex records cannot be CNAMEs

example.com itself must use an A record (or an ALIAS/ANAME if your provider supports flattening). Use a CNAME for www and other subdomains. TTL 300 is a good default while you are setting things up.

Verify DNS before you blame the certificate

From any machine, ask the public resolver directly rather than trusting a browser cache:

bash
dig +short hello.example.com A
dig +short hello.example.com AAAA
dig +short hello.example.com CNAME
dig +trace hello.example.com | tail -20

The A answer must be the server that terminates TLS. An old AAAA record is a common cause of “it works on IPv4 but not IPv6”; remove it if the server has no IPv6 address. To query a specific resolver:

bash
dig @1.1.1.1 +short hello.example.com
dig @8.8.8.8 +short hello.example.com

Once the record resolves, request the host and watch the response and the certificate:

bash
curl -I https://hello.example.com
echo | openssl s_client -connect hello.example.com:443 -servername hello.example.com 2>/dev/null | openssl x509 -noout -subject -dates
dok certs list

Certificate issuance

In built-in edge mode, dok answers ACME HTTP-01 challenges on :80 and TLS-ALPN-01 on :443, and stores certificates under <data>/acme. The host set is recomputed every 15 seconds, so a newly added domain is picked up without a restart; the TLS listener is swapped with SO_REUSEPORT so existing connections are not dropped.

When dok runs behind Traefik or Caddy, the external proxy owns TLS. dok writes exact Host() routers (when --traefik-dir is set) so the proxy can request a certificate on first request. In that mode dok certs renew returns a conflict explaining that renewal belongs to the proxy.

What certificate states mean
StateMeaningWhat to do
IssuedA certificate exists and is not close to expiry.Nothing. Renewal is automatic.
ExpiringExpires within 14 days; dok marks it in the UI.Check that ports 80/443 are reachable; request a renewal.
PendingNo certificate yet, or the last order failed.Verify DNS, firewall, and any proxy in front of dok.
ExternalTLS is terminated by Traefik/Caddy, not dok.Look at the proxy's certificate resolver and logs.

Issuance is usually seconds after DNS resolves. Let's Encrypt applies rate limits, so repeated forced renewals can delay a fix. A staging certificate (--acme-staging) is deliberately untrusted by browsers; it is only for testing.

Apex, www and redirects

Add both hostnames to the project, then choose one canonical direction:

bash
dok domain hello example.com
dok domain hello www.example.com
dok proxy set hello --redirect www-to-apex --force-https
dok proxy show hello
  • --redirect www-to-apex sends www.example.com to example.com.
  • --redirect apex-to-www does the reverse.
  • --force-https redirects HTTP to HTTPS at the proxy.
  • --header "Name: value" adds response headers; --basic-user/--basic-password protect a staging site.

Both hostnames still need their own DNS record and their own certificate. A redirect does not make the second hostname resolve.

Remove a domain

bash
dok domains list hello
dok domains rm hello old.example.com

dok domains rm removes an extra domain or clears the primary. Once the primary is cleared, the default <app>.<base-domain> host is routed again. The route stops immediately; the certificate file is left in place and expires naturally. You can delete the DNS record after traffic has drained.

Troubleshooting

Common domain and certificate failures
SymptomLikely causeCheck / fix
NXDOMAINRecord missing, typo, or wrong zone.dig +short the exact name; confirm the registrar's nameservers with dig NS.
Resolves to the wrong IPStale A/AAAA, CNAME flattening, or a CDN proxy.Compare dig A and dig AAAA with the server address. Remove stale records.
Works for some people onlyPropagation or a low-TTL cache.Query @1.1.1.1 and the authoritative nameserver; wait for the old TTL.
Certificate stays pendingPorts 80/443 blocked, DNS points elsewhere, or a proxy intercepts ACME.curl -I http://host/.well-known/acme-challenge/x; open the firewall; use DNS-only mode at the CDN.
CAA forbids issuanceThe zone has a CAA record that excludes Let's Encrypt.dig CAA example.com; allow letsencrypt.org or remove the restriction.
Cloudflare shows 52xOrange-cloud proxy cannot reach the origin or blocks TLS-ALPN-01.Set the record to DNS-only while issuing; re-enable the proxy afterwards if the origin supports it.
Wildcard certificate wanteddok does not implement DNS-01.Use an external Traefik/Caddy with a DNS-01 wildcard and run dok behind it.
“host is reserved”You targeted the dashboard host or the base-domain apex.Choose a different hostname; those names belong to the control plane.
“domain belongs to another project”The host is already attached elsewhere.dok domains list on the other project, then remove it there first.
